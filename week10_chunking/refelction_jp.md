## Step 1：JSQuAD をテスト用に作り直す

### なぜ JSQuAD か

チャンキングを評価するには、この3つが必要：

1. 長い文書
2. 質問
3. 答えの正確な位置

JQaRA はもうパッセージが切られていて、これ以上切るものがない。JSQuAD なら質問と答えの位置（`answer_start`）があるので、こっちに切り替えた。

> JSQuAD = SQuAD（Stanford Question Answering Dataset）の日本語版。Yahoo Japan と早稲田大学が作った JGLUE の一部。

### 読み込みでハマったところ

新しい `datasets` はスクリプト型のデータセットに対応してなくて、JGLUE も JaQuAD も読めなかった：

```
RuntimeError: Dataset scripts are no longer supported, but found JGLUE.py
```

対処：GitHub から生の JSON を直接落とす。

```python
!wget -O jsquad_train.json "https://raw.githubusercontent.com/yahoojapan/JGLUE/main/datasets/jsquad-v1.3/train-v1.3.json"
```

### 元データの形式（SQuAD 形式）

記事（`title`）→ 段落（`context`）→ 質問（`question` + `answers[text, answer_start]`）

```json
{
  "data": [
    {
      "title": "造語",
      "paragraphs": [
        {
          "context": "造語 [SEP] 造語（ぞうご）は、新たに語（単語）を造ることや、既存の語を組み合わせて新たな意味の語を造ること、また、そうして造られた語である。…",
          "qas": [
            {
              "question": "新たに語（単語）を造ることや、既存の語を組み合わせて新たな意味の語を造ること",
              "id": "a1000888p0q0",
              "answers": [
                { "text": "造語", "answer_start": 0 }
              ],
              "is_impossible": false
            }
          ]
        }
      ]
    }
  ]
}
```

- 一番外側のキーは `data` だけ
- `context` は必ず `タイトル [SEP] ` で始まる（自分の中では「シール」と呼んでる。これは剥がす）
- `answer_start` は `context` の0文字目から数えた位置で、シール部分も含む

### 加工後の形式（`jsquad_docs.json`）

```json
[
  {
    "title": "造語",
    "doc": "造語（ぞうご）は、新たに語…\n（第2段落の本文）\n…",
    "qas": [
      {
        "question": "新たに語（単語）を造ることや、…",
        "answer": "造語",
        "start": 0,
        "end": 2
      }
    ]
  }
]
```

- `doc`：同じ記事の段落からシールを剥がして、改行でつないだ長い文書
- `start` / `end`：`doc` の中での答えの位置。`doc[start:end] == answer` になる

### `build_doc` のロジック

1. 各段落の頭に `タイトル [SEP] ` のシールがあるので剥がす
2. 答えの位置からシールの長さを引く（例：`造語 [SEP] ` = 9文字）
3. マイナスになったら、答えがシールの上にラベル付けされてたということ → 本文の中を探す。見つからなければその質問は捨てる
4. 長い文書での位置に変換：`offset + 本文内の位置`
5. 段落を1つ処理し終わったら `offset += 段落の長さ + 1`（+1 は改行の分）
6. 本文を全部改行でつないで `doc` にする
7. 確認：`doc[start:end] == 答え`

> ⚠️ よくやるミス
> - `offset` を更新するタイミングを間違える（その段落の質問を全部処理してから）
> - +1 を忘れる

### チェック結果

| | |
|---|---|
| 記事数 | 710 |
| 元の質問数 | 62,697 |
| 残った質問数 | 59,568（95%） |
| start > 0 | 79.5% |
| start = 0 | 9.3% |
| start < 0（答えがシール上） | 11.1%（うち5%は捨てた） |
| 文書の長さ（文字） | 最短 48／中央値 2,264／75% 5,048／最長 59,624 |
| 確認失敗 | 0（約6万問のラベルが全部合ってる） |

### 限界（正直、結果より大事）

1. 捨てた5%はランダムじゃない。ほぼ全部「答え＝記事タイトル」タイプの質問。
2. 質問は1つの段落だけを見て作られてるので、複数の段落をまたぐ問題がない。たぶん小さいチャンクが有利になる。
3. 原文とほぼ同じ言い回しの質問が多いので、実際より検索しやすい。
4. Wikipedia の文体で、ビジネス文書じゃない。
5. JSQuAD の本来の使い方じゃなくて、作り直したもの。他の人の数字とは比べられない。
6. 長い文書ほど質問が多いので、全体スコアが長い文書に引っぱられる。「質問ごと」と「文書ごと」の平均を両方出すべき。

## Step 2：分断率

分断率 = 答えがどのチャンクにも丸ごと入っていない割合。つまり答えのど真ん中で切れてしまったケース。

### 先に予測する

$$
\text{分断率} \approx \frac{\text{答えの長さ} - 1}{\text{チャンクの長さ}}
$$

答えの長さ：中央値 5文字、平均 6.1文字、最長 19文字。

### 結果

| L | 予測 | 実測（オーバーラップなし） | 実測（15% オーバーラップ） |
|---|---|---|---|
| 200 | 2.57% | 2.56% | 0.00%（overlap = 30） |
| 400 | 1.28% | 1.24% | 0.00%（overlap = 60） |
| 800 | 0.64% | 0.59% | 0.00%（overlap = 120） |

### 考えたこと

- 予測と実測がほぼ一致。考え方もコードも合ってたっぽい
- 実測のほうが少し低くて、L が大きいほど差が広がる。L より短い文書には切れ目自体がないから、だと思う。まだ確認してない
- オーバーラップが 18（最長の答え − 1）以上なら絶対に切れない。なので 30／60／120 はどれも十分。むしろ多すぎ
- オーバーラップはタダじゃない：チャンクが増える、埋め込みも増える、検索結果がほぼ重複しがち
- オーバーラップのもう一つの役割（切れ目の前後の文脈を残す）は分断率では見えない。Step 3 で見るしかない

### まとめ

JSQuAD だと、答えが切れる問題はほぼ気にしなくていい。このステップはただのサニティチェック。

ただ、ビジネス／法務／行政の文書だと、「答え」が150文字くらいの条文になることも普通にある。それを式に入れると、L = 200 で分断率はだいたい75%。仕組みは同じなのに結論が真逆になるので、ここは気をつけたい。

## ほかに覚えたこと

### ベンチマークとアブレーション

- ベンチマーク：テストそのもの（問題 + 採点のしかた）
- アブレーション：そのテストを使って、一度に一つだけ変えながらやり方を比べること

### チャンキングは RAG だけのものじゃない

普通の検索、長い文書の要約、契約書からの条項抽出、事前学習（nanoGPT の `block_size` も実はチャンキング）。目的が違えば「いい切り方」の基準も変わる。

### マルチモーダル・チャンキング

表・図・スキャンしたページがある文書向け。よくあるやり方は3つ：

1. まずテキストに変換して、レイアウトに沿って切る
2. VLM に説明文を書かせて、それで検索する
3. ページ画像をそのまま埋め込む

テキスト版のあとでやる予定。でも JD との関係は staleness より強い。

### RAG の評価指標（Week 13 の予習）

| 側 | 指標 | 意味 |
|---|---|---|
| 検索 | context precision | 取ってきたもののうち、どれだけ関係あるか |
| 検索 | context recall | 必要なものがちゃんと取れてるか |
| 生成 | faithfulness | 答えがパッセージに裏付けられてるか |
| 生成 | answer relevance | ちゃんと質問に答えてるか |

- RAGAS は LLM を採点役に使うので、まず手でラベル付けした少量のサンプルで、採点役が信用できるか確かめたほうがいい
- faithfulness ≠ 正しい。パッセージ自体が間違ってたら、「忠実」な答えでもやっぱり間違い

### 別のデータに移すとき

指標とやり方はそのまま使える。ただ：

- ラベルは作り直し（ここが一番時間かかる）
- 「答え」の定義も変える必要があるかも（長い条文、あちこちに散らばった根拠、表）
